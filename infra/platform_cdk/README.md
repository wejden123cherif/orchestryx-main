# Orchestryx Platform CDK

This CDK app defines the long-lived Orchestryx platform foundation: VPC, ECR, queues, Cognito, ECS, database, private DNS, VPN foundation, and CloudWatch log groups.

It is the only active infrastructure-as-code entry point in this repository. The old per-lab EC2 CDK app has been removed, and lab runtime provisioning is currently disabled until a new runtime is implemented deliberately.

## Environments

Environment config lives in:

- `config/dev.yaml`
- `config/staging.yaml`
- `config/prod.yaml`

The config files use `${CDK_DEFAULT_ACCOUNT}` and `${CDK_DEFAULT_REGION}` placeholders instead of hardcoded account or region values. Set those through normal CDK credentials/profile selection.

## Synth

From the repo root on Windows:

```powershell
.venv\Scripts\activate
cd infra\platform_cdk
cdk synth -c env=dev
```

From Linux/macOS/WSL:

```bash
source .venv/bin/activate
cd infra/platform_cdk
cdk synth -c env=dev
```

Use `-c env=staging` or `-c env=prod` to load the other config files.

## Dev Bring-Up Runbook

`config/dev.yaml` uses `orchestryx-dev-*` resource names and stack IDs prefixed
with `OrchestryxDev-*`, so dev does not collide with prod/manual names such as
`orchestryx-api` or `orchestryx-worker`.

The minimum dev stack set for running the platform is:

- `NetworkStack`
- `EcrStack`
- `QueuesStack`
- `AuthStack`
- `ObservabilityStack`
- `DatabaseStack`
- `EcsPlatformStack` (includes ALB, API/worker services, one-off migration task definition)
- `DnsStack`
- `VpnStack`

`EcsPlatformStack` now provisions:
- An internet-facing Application Load Balancer (`alb.enabled: true` in dev.yaml)
- A one-off Alembic migration task definition (same image/role as API, invoked explicitly)

The API starts in degraded mode if migrations have not run (`/health` returns 200,
`/ready` returns 503).  Run the migration task before expecting `GET /catalog` or
any DB-backed route to work.

Dev enables:

- `database.enabled: true`
- `ecs.services_enabled: true`

For a clean AWS account, use a bootstrap sequence. ECS services reference ECR
images and the runtime secret, so the repositories and foundation outputs must
exist before the services can run successfully.

```powershell
cd infra\platform_cdk

cdk synth -c env=dev
cdk diff -c env=dev

# Phase 1: deploy all foundation stacks (network through database).
# VpnStack is included because it is enabled in dev.yaml.
# Do NOT include EcsPlatformStack yet — images must exist before services start.
cdk deploy OrchestryxDev-NetworkStack OrchestryxDev-EcrStack OrchestryxDev-QueuesStack OrchestryxDev-AuthStack OrchestryxDev-ObservabilityStack OrchestryxDev-DatabaseStack OrchestryxDev-DnsStack OrchestryxDev-VpnStack -c env=dev --outputs-file cdk-outputs-dev.json
python export_env.py --env dev --outputs-file cdk-outputs-dev.json

cd ..\..

# Phase 2: push initial images to ECR.
# Use the "images" target — it only builds and pushes; it does NOT call ecs update-service.
# Safe to run before EcsPlatformStack is deployed.
$env:ORCHESTRYX_ENV = "dev"
.\scripts\windows\deploy.ps1 images

# Phase 3: create the runtime secret used by ECS tasks.
# The secret name in dev is orchestryx/dev/api/env (runtime_secret_name in config/dev.yaml).
#
# Retrieve the RDS credentials generated by Aurora:
#   $secretArn = (Get-Content .env.dev.generated | Select-String ORCHESTRYX_DATABASE_SECRET_ARN).ToString().Split("=",2)[1]
#   aws secretsmanager get-secret-value --secret-id $secretArn --region eu-central-1
#
# Build DATABASE_URL:
#   postgresql+asyncpg://<username>:<password>@<ORCHESTRYX_DATABASE_ENDPOINT>:5432/orchestryx?ssl=require
#
# Create or update the secret (replace values from the step above):
#   aws secretsmanager create-secret --name orchestryx/dev/api/env --region eu-central-1 `
#     --secret-string '{"DATABASE_URL":"postgresql+asyncpg://...","DB_SSL_MODE":"require","SQL_ECHO":"false",...}'
# Or update if it already exists:
#   aws secretsmanager put-secret-value --secret-id orchestryx/dev/api/env --region eu-central-1 `
#     --secret-string '{"DATABASE_URL":"postgresql+asyncpg://...",...}'

# Phase 4: deploy EcsPlatformStack (safe now that images exist).
# This creates the ALB, API/worker services, and migration task definition.
# API will start in degraded mode (/ready → 503) until migrations run.
cd infra\platform_cdk
cdk deploy OrchestryxDev-EcsPlatformStack -c env=dev --outputs-file cdk-outputs-dev.json
python export_env.py --env dev --outputs-file cdk-outputs-dev.json

cd ..\..

# Phase 5: run Alembic migrations inside ECS Fargate.
# Aurora is in a private isolated subnet — never run alembic from a laptop.
# The migration task uses the same image, security group, and secret as the API.
.\scripts\windows\run-migrations.ps1
# On Linux/macOS/WSL: ./scripts/linux/run-migrations.sh

# Phase 6: restart the API service so it picks up the migrated schema.
# The script prints the exact restart command; or run it manually:
#   aws ecs update-service --cluster orchestryx-dev --service orchestryx-dev-api-service --force-new-deployment --region eu-central-1
.\scripts\windows\deploy.ps1 api

# Phase 7: verify the API is healthy.
# Check ALB target group health:
#   aws elbv2 describe-target-health --target-group-arn <TargetGroupArn> --region eu-central-1
# Check /health (always 200) and /ready (200 only after migrations):
#   curl http://<ApiLoadBalancerDnsName>/health
#   curl http://<ApiLoadBalancerDnsName>/ready
# ApiLoadBalancerDnsName is in cdk-outputs-dev.json and .env.dev.generated (ORCHESTRYX_API_ALB_DNS)
```

Linux/macOS/WSL equivalents:

```bash
cd infra/platform_cdk
cdk synth -c env=dev
cdk diff -c env=dev

# Phase 1
cdk deploy OrchestryxDev-NetworkStack OrchestryxDev-EcrStack OrchestryxDev-QueuesStack OrchestryxDev-AuthStack OrchestryxDev-ObservabilityStack OrchestryxDev-DatabaseStack OrchestryxDev-DnsStack OrchestryxDev-VpnStack -c env=dev --outputs-file cdk-outputs-dev.json
python export_env.py --env dev --outputs-file cdk-outputs-dev.json

cd ../..

# Phase 2: images only — safe before ECS services exist
ORCHESTRYX_ENV=dev ./scripts/linux/deploy.sh images

# Phase 3: create or update the runtime secret orchestryx/dev/api/env
# (see PowerShell steps above for the exact commands; substitute backtick with \ for bash)

# Phase 4
cd infra/platform_cdk
cdk deploy OrchestryxDev-EcsPlatformStack -c env=dev --outputs-file cdk-outputs-dev.json
python export_env.py --env dev --outputs-file cdk-outputs-dev.json

cd ../..

# Phase 5: run migrations via ECS Fargate (never from laptop — Aurora is private)
./scripts/linux/run-migrations.sh

# Phase 6: restart API so it picks up the migrated schema
ORCHESTRYX_ENV=dev ./scripts/linux/deploy.sh api

# Phase 7: verify
# curl http://$ORCHESTRYX_API_ALB_DNS/health
# curl http://$ORCHESTRYX_API_ALB_DNS/ready
```

This writes `.env.dev.generated` at the repo root. It is ignored by git.

Verify after deployment:

```bash
aws ecs describe-services \
  --cluster "$ORCHESTRYX_ECS_CLUSTER_NAME" \
  --services "$ORCHESTRYX_API_SERVICE_NAME" "$ORCHESTRYX_WORKER_SERVICE_NAME" \
  --region "$AWS_REGION"

aws logs tail /ecs/orchestryx-dev-api --since 15m --region "$AWS_REGION"
aws logs tail /ecs/orchestryx-dev-worker --since 15m --region "$AWS_REGION"

curl http://<dev-api-endpoint>/health
```

## Recovering from a Broken Migration State

If a migration fails partway through (e.g. a `DuplicateTableError`, a partial schema,
or a corrupted `alembic_version` table), the fastest recovery path in dev is:

1. **Reset the schema** — drops and recreates the public schema inside ECS Fargate
   (Aurora is private; no laptop access):

   ```powershell
   # Windows
   .\scripts\windows\reset-dev-db.ps1
   # With -Force to skip the confirmation prompt:
   .\scripts\windows\reset-dev-db.ps1 -Force
   ```

   ```bash
   # Linux / macOS / WSL
   ./scripts/linux/reset-dev-db.sh
   # With --force to skip the confirmation prompt:
   ./scripts/linux/reset-dev-db.sh --force
   ```

2. **Re-run migrations** to rebuild the schema from scratch:

   ```powershell
   .\scripts\windows\run-migrations.ps1
   ```

   ```bash
   ./scripts/linux/run-migrations.sh
   ```

3. **Restart the API** so it picks up the fresh schema:

   ```powershell
   .\scripts\windows\deploy.ps1 api
   ```

   ```bash
   ORCHESTRYX_ENV=dev ./scripts/linux/deploy.sh api
   ```

4. **Verify** that `/ready` returns 200:

   ```bash
   curl http://$ORCHESTRYX_API_ALB_DNS/ready
   ```

The reset scripts run the Python DROP/CREATE SCHEMA sequence inside the migration
container (same image and secret as the API), so they have identical Aurora access
without any VPN or bastion host.  They refuse to run unless `ORCHESTRYX_ENV=dev`.

## HTTPS and Vercel DNS Setup

Orchestryx uses Vercel for the frontend (`orchestryx.cloud`, `www.orchestryx.cloud`) and
AWS ALB for the backend API (`api.orchestryx.cloud`).  There is no Cloudflare layer.

### ACM certificate

The ACM certificate for `api.orchestryx.cloud` is in `eu-central-1` (same region as the
ALB, which is required for ALB certificates).  It is referenced directly in
`config/dev.yaml` under `alb.certificate_arn`.

The certificate requires a DNS CNAME validation record.  AWS Console → ACM → the
certificate → "Create records in Route 53" does **not** apply here because DNS is
managed by Vercel.  Add the ACM-provided CNAME in Vercel DNS manually:

| Type | Name | Value |
|------|------|-------|
| CNAME | `_acm-challenge.api` (or the exact name ACM shows) | `<validation-value>.acm-validations.aws.` |

Check the current validation status:

```bash
aws acm describe-certificate \
  --certificate-arn arn:aws:acm:eu-central-1:254076817005:certificate/6c40284c-f70e-4841-8c03-4347237b6e03 \
  --region eu-central-1 \
  --query "Certificate.DomainValidationOptions"
```

### Vercel DNS records

Add these records in the Vercel project DNS panel for `orchestryx.cloud`:

| Type | Name | Value | Notes |
|------|------|-------|-------|
| CNAME | `api` | `orchestryx-dev-api-alb-736505199.eu-central-1.elb.amazonaws.com` | Routes `api.orchestryx.cloud` to the ALB |

Vercel automatically serves `orchestryx.cloud` and `www.orchestryx.cloud` — no
additional DNS records are needed for the frontend.

### Vercel frontend environment variables

In the Vercel project settings → Environment Variables, set for **Production**:

```
NEXT_PUBLIC_API_URL=https://api.orchestryx.cloud
```

For Preview deployments, set it to the preview ALB URL or a staging equivalent so
that preview branches also work end-to-end.

### Backend CORS configuration

The runtime secret `orchestryx/dev/api/env` in Secrets Manager must include:

```json
"CORS_ALLOWED_ORIGINS": "https://orchestryx.cloud,https://www.orchestryx.cloud,https://<your-vercel-preview-domain>.vercel.app"
```

Update the secret via CLI:

```bash
aws secretsmanager put-secret-value \
  --secret-id orchestryx/dev/api/env \
  --region eu-central-1 \
  --secret-string "$(
    aws secretsmanager get-secret-value \
      --secret-id orchestryx/dev/api/env \
      --region eu-central-1 \
      --query SecretString \
      --output text \
    | python3 -c "
import json, sys
s = json.load(sys.stdin)
s['CORS_ALLOWED_ORIGINS'] = 'https://orchestryx.cloud,https://www.orchestryx.cloud'
print(json.dumps(s))
"
  )"
```

After updating the secret, force a new API deployment so ECS picks it up:

```powershell
.\scripts\windows\deploy.ps1 api
```

```bash
ORCHESTRYX_ENV=dev ./scripts/linux/deploy.sh api
```

### Verification

Once the CNAME propagates and ACM validation is `SUCCESS`:

```bash
# Health check (always 200)
curl https://api.orchestryx.cloud/health

# Ready check (200 after migrations have run)
curl https://api.orchestryx.cloud/ready

# Confirm HTTP redirects to HTTPS
curl -I http://api.orchestryx.cloud/health
# Expected: HTTP/1.1 301 Moved Permanently → Location: https://api.orchestryx.cloud/health
```

## App Deployment Boundary

`infra/platform_cdk/` owns infrastructure: VPC, ECR, SQS, Cognito, ECS cluster,
task roles, task definitions, services, database, DNS foundation, and log
groups.

`scripts/linux/deploy.sh` and `scripts/windows/deploy.ps1` only deploy
application images to infrastructure that already exists. They build API/worker
images, tag and push them to ECR, force ECS service redeployments, and can wait
for service stability. They do not create IAM roles, attach policies, create
load balancers, create services, or call the legacy setup scripts.

## Deployment Safety

This app is a foundation, not an immediate production migration.

Several resources in `config/prod.yaml` intentionally mirror current manual names such as `orchestryx-api`, `orchestryx-worker`, `orchestryx`, and `orchestryx-db`. If those resources already exist, a direct `cdk deploy` will fail with name conflicts or require an import workflow. Do not deploy over existing production resources without a migration plan.

Safe migration patterns:

1. Use `cdk import` for resources that should keep their current physical names.
2. Deploy to a new environment name first, validate, then cut traffic over.
3. Keep `services_enabled: false`, `database.enabled: false`, and `vpn.enabled: false` until imports or replacements are planned.
4. Compare synthesized templates against `scripts/aws/` manifests before changing live services.

## Stack Map

- `network_stack.py`: creates the VPC, public subnets, private subnets, isolated subnets, and NAT gateways.
- `ecr_stack.py`: creates API and worker ECR repositories.
- `queues_stack.py`: creates provision and destroy SQS queues.
- `auth_stack.py`: creates the Cognito user pool and web app client.
- `observability_stack.py`: creates ECS CloudWatch log groups.
- `database_stack.py`: creates the database security group and can create Aurora PostgreSQL when `database.enabled` is true.
- `ecs_platform_stack.py`: creates the ECS cluster, task roles, execution role, API/worker security groups, and optional API/worker Fargate services when `ecs.services_enabled` is true.
- `dns_stack.py`: creates the private hosted zone foundation.
- `vpn_stack.py`: creates the WireGuard gateway security group and role; the instance is created only when `vpn.enabled` is true.

## Manual Resource Replacement Map

The existing `scripts/aws/` folder and `scripts/*/setup-aws.*` scripts remain
legacy/manual infrastructure references. They are kept for comparison and safe
migration only; the recommended path is platform CDK first, then app deploy.

- `scripts/aws/ecr/repositories.json` -> `EcrStack`
- `scripts/aws/ecs/services.json` -> `EcsPlatformStack`
- `scripts/aws/task-definitions/*.json` -> `EcsPlatformStack` and `constructs/fargate_service.py`
- `scripts/aws/iam/*.json` -> `EcsPlatformStack`
- `scripts/aws/security-groups/security-groups.json` -> `DatabaseStack`, `EcsPlatformStack`, and `VpnStack`
- `scripts/aws/rds/database.json` -> `DatabaseStack`
- `scripts/aws/logs/log-groups.json` -> `ObservabilityStack`
- `scripts/aws/secrets/secrets.json` -> imported runtime secret used by `EcsPlatformStack`
